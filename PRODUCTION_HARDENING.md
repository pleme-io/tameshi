## CRITICAL: Configuration Integrity (Input Poisoning)

> **This is the single most overlooked attack vector in supply-chain security.**
> A verified binary fed malicious configuration is a verified weapon.

### The Problem

Tameshi proves the Code (Nix derivation), the Secrets (Akeyless policy), and the
Runtime (kanshi eBPF). But most applications read configuration from ConfigMaps,
Secrets, environment variables, or PersistentVolumes.

An attacker who cannot modify the binary can instead:
- Change `DB_HOST` in a ConfigMap to point to a malicious database
- Modify `LOG_LEVEL=debug` to exfiltrate data via verbose logging
- Add a sidecar proxy in a Helm values override
- Inject environment variables via a mutating webhook

**The binary is "proven," but its behavior is hijacked.**

### The Fix: Configuration-as-Code in the Merkle Tree

**Every ConfigMap, Secret reference, and environment variable used by a pod MUST
be included as a leaf node in the Merkle tree.**

If the configuration changes by even one byte, the Merkle root changes, and
sekiban rejects the deployment.

### Implementation: Helm Rendered State Hashing

**This is the critical architectural decision:**

The Helm chart collector (`tameshi/src/collectors/helm.rs`) MUST hash the
**fully rendered** Helm output — not just the chart templates, but the actual
YAML that Helm produces after value substitution. This rendered output contains:

1. All ConfigMap definitions (with their `data:` sections)
2. All Secret references (by name, not value — see policy-path hashing)
3. All environment variables set on containers
4. All volume mounts and volume definitions
5. All resource limits, security contexts, service accounts
6. All labels, annotations, and selectors

```bash
# The attestation pipeline MUST hash the rendered output:
helm template my-release ./chart -f values-production.yaml | \
  tameshi hash --mode logical --format yaml
```

### Two Paths to Configuration Integrity

#### Path 1: Helm Rendered Hashing (Recommended for K8s-native workloads)

```
helm template → rendered YAML → YamlCanonicalizer (Logical mode) → BLAKE3 → Merkle leaf
```

The Helm collector hashes the fully-rendered manifests. This captures:
- Template logic resolution (if/else, range, etc.)
- Value substitution (from values.yaml, --set flags, etc.)
- ConfigMap and Secret definitions (the actual data)
- All K8s resource specifications

**Files affected:**
- `tameshi/src/collectors/helm.rs` — add `hash_rendered_chart()` function
- New function: runs `helm template` and hashes the sorted, canonical YAML output
- Existing `hash_chart_dir()` remains for chart-level attestation
- Both hashes become separate leaf nodes: `helm-chart` and `helm-rendered`

#### Path 2: Nix Derivation Hashing (Recommended for Nix-managed workloads)

```
nix build .#k8s-manifests → /nix/store/... → hash_closure() → BLAKE3 → Merkle leaf
```

For workloads where Helm charts are generated from Nix (the pleme-io pattern),
the Nix closure hash ALREADY captures the full configuration state because:
- Nix derivations are content-addressed (any input change = different hash)
- Helm values files are Nix inputs → changing a value changes the derivation
- ConfigMap content is generated by Nix → included in the closure

**This means:** For Nix-managed workloads, the existing Nix collector already
provides configuration integrity. The Helm rendered hash is defense-in-depth.

### What Gets Hashed (Explicit Enumeration)

| Configuration Source | Hashed By | Leaf Node |
|---------------------|-----------|-----------|
| ConfigMap `data:` | Helm rendered / Nix closure | `helm-rendered` or `nix` |
| Secret references (names, not values) | Helm rendered / Akeyless collector | `helm-rendered` + `akeyless` |
| Environment variables | Helm rendered / Nix closure | `helm-rendered` or `nix` |
| Volume mounts | Helm rendered / Nix closure | `helm-rendered` or `nix` |
| Resource limits / requests | Helm rendered / Nix closure | `helm-rendered` or `nix` |
| Security context (runAsUser, etc.) | Helm rendered / Nix closure | `helm-rendered` or `nix` |
| Service account | Helm rendered / Nix closure | `helm-rendered` or `nix` |
| Network policies | Helm rendered / Nix closure | `helm-rendered` or `nix` |
| Init containers / sidecars | Helm rendered / Nix closure | `helm-rendered` or `nix` |

Configuration integrity maps directly to NIST 800-53 controls:

| NIST Control | Description | Tameshi Implementation |
|--------------|-------------|----------------------|

3. Environment variables match the rendered Helm output
4. Security contexts match the attested specification

## The Bootstrap Protocol ("Chicken-and-Egg" Problem)

### The Problem

When a K8s cluster restarts cold, sekiban itself needs to start before it can
enforce admission control. But if sekiban requires attestation to deploy, how
does sekiban deploy itself?

### The Fix: Static Admission Path

The `tameshi-system` namespace uses a pre-signed, offline-verified attestation:

1. **Build-time:** inshou produces a signed attestation for sekiban + kensa + kanshi
   during CI/CD. This attestation is embedded in the Helm chart as a ConfigMap.

2. **Bootstrap sequence:**
   ```
   a. K8s API server starts (no webhook registered yet)
   b. FluxCD deploys tameshi-system namespace (no admission control)
   c. sekiban starts, registers its webhook
   d. sekiban reads its own attestation from the embedded ConfigMap
   e. sekiban verifies its own integrity (self-attestation)
   f. From this point, all other namespaces are gated
   ```

3. **Self-attestation verification:**
   - sekiban hashes its own binary at startup
   - Compares against the embedded attestation
   - If mismatch → refuses to start, logs critical alert
   - If match → registers webhook, begins enforcement

### Helm Chart Configuration

```yaml
# chart/sekiban/templates/self-attestation.yaml
apiVersion: v1
kind: ConfigMap
metadata:
  name: sekiban-self-attestation
  namespace: tameshi-system
data:
  attestation.json: |
    {
      "binary_hash": "blake3:...",
      "nix_closure_hash": "blake3:...",
      "helm_rendered_hash": "blake3:...",
      "merkle_root": "blake3:...",
      "signed_at": "2026-03-20T00:00:00Z",
      "signer": "ci-pipeline"
    }
```

|--------------|----------------------|

## Resilient Admission Control (CEL Fail-Safe)

### The Problem

If the sekiban webhook pod crashes, restarts, or has a network partition, the
K8s API server cannot reach it. Default K8s behavior: `failurePolicy: Fail`
blocks all deployments. `failurePolicy: Ignore` creates a security bypass.

### The Fix: Multi-Tier Defense

**Tier 1: sekiban webhook** (primary enforcement)
- Full Merkle root verification
- Changeset hashing
- Compliance hash checking

**Tier 2: ValidatingAdmissionPolicy (CEL)** (fail-safe)
- K8s 1.30+ native feature (no external webhook needed)
- CEL expressions verify that required annotations exist
- Cannot do full Merkle verification, but can enforce annotation presence
- Survives webhook outages because it runs inside the API server

```yaml
# Tier 2: CEL-based fail-safe
apiVersion: admissionregistration.k8s.io/v1
kind: ValidatingAdmissionPolicy
metadata:
  name: tameshi-annotation-guard
spec:
  failurePolicy: Fail
  matchConstraints:
    resourceRules:
    - apiGroups: ["apps"]
      apiVersions: ["v1"]
      operations: ["CREATE", "UPDATE"]
      resources: ["deployments"]
  validations:
  - expression: >-
      has(object.metadata.annotations) &&
      'sekiban.pleme.io/signature' in object.metadata.annotations &&
      object.metadata.annotations['sekiban.pleme.io/signature'].startsWith('blake3:')
    message: "Deployment must have a valid sekiban.pleme.io/signature annotation"
  - expression: >-
      has(object.metadata.annotations) &&
      'sekiban.pleme.io/certification-hash' in object.metadata.annotations
    message: "Deployment must have a sekiban.pleme.io/certification-hash annotation"
```

**Tier 3: Break-Glass mechanism** (emergency bypass)
- See PROVISIONING_AND_REVOCATION_SPEC.md, Hole 4

### Failure Mode Matrix

| Scenario | Tier 1 (webhook) | Tier 2 (CEL) | Result |
|----------|------------------|--------------|--------|
| Normal operation | Active | Active | Full verification |
| Webhook restart | Down (30s) | Active | Annotation-only check |
| Webhook crash loop | Down | Active | Annotation-only check + alert |
| Full outage | Down | Active | Annotation-only check + break-glass |
| CEL misconfigured | Active | Inactive | Full verification (Tier 1 sufficient) |

## Architecture-Aware Attestations (Multi-Arch Identity)

### The Problem

Modern K8s clusters run mixed architectures: x86_64 (Intel/AMD) and ARM64
(AWS Graviton, Apple Silicon). The same application compiled for different
architectures produces different binaries with different BLAKE3 hashes.

If the Merkle tree only contains the x86 hash, ARM nodes reject the deployment.

### The Fix: Architecture-Keyed Binary Map

The Merkle tree's binary leaf is not a single hash — it's an architecture map:

```rust
// tameshi/src/signature.rs — ArchitectureMap
pub struct ArchitectureAttestation {
    pub attestations: BTreeMap<Architecture, Blake3Hash>,
}

pub enum Architecture {
    X86_64,
    Aarch64,
    // Future: riscv64, s390x
}
```

**Merkle tree structure:**
```
Root
├── nix (closure hash — architecture-specific)
├── oci (manifest digest — multi-arch via OCI index)
│   ├── linux/amd64: blake3:aaa...
│   └── linux/arm64: blake3:bbb...
├── helm-rendered (architecture-independent)
├── kubernetes (architecture-independent)
├── akeyless (architecture-independent)
└── configuration (architecture-independent)
```

### OCI Multi-Arch Support

OCI already has multi-arch manifests (OCI Index / Docker Manifest List).
The OCI collector hashes the **index manifest** (which contains per-platform
digests), not individual platform images. This means:

1. The OCI layer hash is stable across architectures
2. Each platform's digest is verifiable via the index
3. sekiban verifies the platform-specific digest matches the running node's arch

### Implementation

- `tameshi/src/collectors/oci.rs` — hash OCI index manifest, include per-platform digests
- `sekiban/src/webhook/admission.rs` — read node architecture from admission request,
  verify against architecture-specific hash
- `inshou/src/gate.rs` — produce per-architecture attestations during CI

## Root of Trust: TPM 2.0 Remote Attestation

### The Problem

kanshi (the eBPF sentinel) lives inside the Linux kernel. But if the node itself
is compromised at the firmware level (BIOS/UEFI/bootloader), the kernel can be
tricked into lying about eBPF program status.

**Your "Proven State" is reported by a potentially "Lying OS."**

### The Fix: Hardware Root of Trust (Phase 3 Roadmap)

For production deployment at enterprise scale, nodes MUST prove their hardware
integrity before receiving Tameshi Merkle keys:

1. **TPM 2.0 Remote Attestation:**
   - Node's TPM generates a quote (signed PCR values)
   - Quote is sent to an attestation server (Akeyless or dedicated)
   - Server verifies the quote against known-good PCR values
   - Only after verification does the node receive the Merkle root keys

2. **Measured Boot Chain:**
   ```
   TPM PCR[0] ← BIOS/UEFI measurement
   TPM PCR[4] ← bootloader measurement
   TPM PCR[5] ← kernel measurement
   TPM PCR[8] ← kanshi eBPF program measurement
   ```

3. **Integration with kanshi:**
   - kanshi extends TPM PCR[14] with the loaded eBPF program hash
   - This creates a hardware-backed proof that kanshi is running unmodified
   - Remote attestation verifies this PCR value

### Roadmap Position

TPM integration is a **Phase 3** item. Current mitigations:
- Secure boot enforcement via cloud provider (AWS Nitro, GCP Shielded VM)
- Node image integrity via OCI hash (same Merkle tree)
- kanshi self-attestation at startup

### NIST Mapping

| NIST Control | Tameshi Implementation |
|--------------|----------------------|
| SC-51 | Hardware-Rooted Integrity — TPM remote attestation |
| SI-7(1) | Integrity Checks — measured boot chain |

## Continuous Runtime Integrity (In-Memory Mutation Defense)

### The Problem

Tameshi verifies binaries at load-time. But once a binary is running, a memory
exploit (buffer overflow, ROP chain, JIT spray) can modify program behavior
in RAM. The binary on disk matches the hash, but the binary in memory is
corrupted.

### The Fix: Periodic Memory Sampling (Phase 3 Roadmap)

kanshi's eBPF sentinel periodically re-hashes executable memory pages:

1. **Sampling Strategy:**
   - kanshi reads `/proc/<pid>/maps` to identify executable segments
   - Periodically (configurable: 1–60 second intervals) hashes `.text` sections
   - Compares against the load-time hash stored in the BPF allow map
   - On mismatch → emit alert + optional kill signal

2. **Performance Considerations:**
   - Only sample `.text` (executable code) segments, not data/heap/stack
   - Use kernel-space page table walks (no context switch)
   - Sampling rate configurable per-namespace via BPF policy map
   - Default: 30-second intervals for critical processes, disabled for others

3. **Limitations (documented honestly):**
   - JIT-compiled code (Java JVM, V8, Python JIT) will have changing `.text`
   - Mitigation: JIT processes use OCI layer + read-only rootfs (see Hole 5)
   - Self-modifying code (rare in server workloads) will trigger false positives
   - Mitigation: allowlist for known self-modifying binaries

### eBPF Implementation Sketch

```rust
// kanshi-ebpf — periodic memory hash verification
// Uses bpf_timer to schedule periodic re-hashing
// Reads process memory pages via bpf_probe_read_kernel
// Compares against tameshi_allow_map entries
```

### Roadmap Position

Memory sampling is a **Phase 3** item. Current mitigations:
- Read-only rootfs prevents on-disk modification
- kanshi `file_open` hooks prevent script replacement
- Namespace isolation limits blast radius

### NIST Mapping

| NIST Control | Tameshi Implementation |
|--------------|----------------------|
| SI-7(6) | Cryptographic Protection — runtime memory verification |
| SI-16 | Memory Protection — periodic integrity checks |

## Updated Merkle Tree Structure

With all hardening items, the complete Merkle tree looks like:

```
Master Root
├── nix (Nix closure hash — content-addressed, includes config)
├── oci (OCI index manifest — multi-arch platform digests)
├── helm-chart (chart templates + Chart.yaml + values.yaml)
├── helm-rendered (CRITICAL: fully rendered manifests — all config state)
├── kubernetes (live manifest hash — canonical YAML)
├── tofu (OpenTofu state — canonical JSON)
├── fluxcd (source commit hash)
├── argocd (git revision hash)
├── akeyless (secret policy paths — not values)
├── akeyless-target (target configuration — 30 types)
├── kindling (identity report)
└── tatara (cluster allocation state)
     +
Compliance Hash (kensa assessment results)
     =
Secure Root (BLAKE3(untested || compliance))
```

**What is proven by this tree:**
1. The code is exactly what was built (nix, oci)
2. The configuration is exactly what was tested (helm-rendered, kubernetes)
3. The secrets policy is untampered (akeyless, akeyless-target)
4. The infrastructure state matches intent (tofu, fluxcd, argocd)
5. The compliance tests passed (kensa hash)
6. The runtime matches the attestation (kanshi eBPF)

**What is NOT proven (by design — see PROVISIONING_AND_REVOCATION_SPEC.md):**
1. The code is free of bugs (Rice's Theorem)
2. The hardware is uncompromised (Phase 3: TPM)
3. Runtime memory is unmodified (Phase 3: memory sampling)

## Impact Statement (For Leadership Review)

1. **Configuration Poisoning is closed.** Every ConfigMap, environment variable,
   and security context is hashed into the Merkle tree via rendered Helm output.
   No attacker can hijack a verified binary with malicious configuration.

2. **Zero single point of failure.** Three-tier admission control (sekiban webhook
   + CEL fail-safe + break-glass) ensures deployments never stall, and security
   never fails open.

3. **Multi-architecture ready.** Architecture-keyed attestations support mixed
   x86/ARM clusters without hash conflicts.

4. **Legally compliant.** Full NIST 800-53 control mapping across CM, SI, SC, SA,
   AU, AC, and IA families. CIRCIA 72-hour evidence chain via heartbeat system.

5. **Honest about boundaries.** Trust Anchor Declaration clearly defines what
   cryptographic proof covers and where human review is required. This is
   mathematical maturity, not hand-waving.
